## Data flow

```text
GitLab signed webhooks ------> durable webhook inbox
                                      |
Bundled directory + GitLab API ---> PostgreSQL snapshots + revision
                                      |
                         injected bootstrap + REST + SSE
                                      |
                                  React Board
```

Production traffic is ready only after directory, members, and board snapshots exist. Go injects the complete authenticated bootstrap into `index.html`; React pre-fills TanStack Query before the first render. `GET /api/v1/bootstrap` is the development fallback and 30-second recovery poll.

Signed Project Issue and Group Member deliveries are committed to a durable PostgreSQL inbox before acknowledgement. The worker fetches canonical GitLab state, then advances a monotonic bootstrap revision in the same transaction as visible changes. PostgreSQL `LISTEN/NOTIFY` fans that revision across app instances, and continuously connected authenticated SSE invalidates TanStack Query in open browsers. Three Board reads back the hooks up, because each answers a question the others cannot. An incremental read every ten seconds asks GitLab only for what changed since the last one. A presence sweep every five minutes enumerates which issues still exist, which is the only way to notice a deletion: GitLab has no webhook for one and an incremental read can never observe an absence. A full re-read every hour catches drift that changes nothing observable, such as a renamed Team label.

## Dependency rule

```text
transport -> application -> domain
infrastructure -> application -> domain
composition root -> all concrete implementations
```

Domain knows no frameworks. Application use cases own narrow consumed ports and transaction boundaries. The file directory, GitLab, and PostgreSQL adapters translate external behavior. Architecture tests enforce this direction.

## Mutations

Card mutations update optimistic `issue_cache` and insert a `durable_operation` in one transaction. New cards receive a temporary negative IID at position zero. The worker resolves the requesting user's encrypted OAuth credential, sends current canonical title, Markdown description, dates, labels, assignees, and lifecycle status through the GitLab Work Item GraphQL API, replaces temporary IIDs after creation, and reconciles responses. Tag edits require one active Team label and never move a card; moves and the explicit status control own lifecycle changes. The fixed lists map by name to `Waiting`, `Inbox`, `To do`, `Doing`, `Review`, and `Done`. A lifecycle missing a status the board maps a lane to fails the read, but a single issue sitting on some other status is quarantined rather than allowed to abort the refresh, and legacy workflow labels are filtered. The join table preserves multiple assignees while deferred foreign keys allow temporary IIDs to become GitLab IIDs. Failed operations keep the optimistic state and can be retried.

Project labels are loaded from GitLab on demand. Comments and system notes use the requesting user's OAuth token for both reads and writes so GitLab permissions and actor attribution remain intact. Comments are not persisted locally or retried by the operation worker; the browser retains a failed draft for manual retry.

## Frontend ownership

TanStack Query owns the bootstrap server snapshot and per-card Comment state. `features/onboarding` owns primary-team confirmation. `features/board` owns transient drafts, the navigable right-side detail drawer, Label selection, Comment composition, the shared GitLab Markdown autocomplete, optimistic mutation, leader bulk-create, multiple-assignee reconciliation, drag/drop and keyboard controls. Quick Actions execute in GitLab through the normal description and Comment writes; the client only discovers commands and inserts valid reference syntax. The Board uses the ordered `Waiting`, `Inbox`, `To do`, `Doing`, `Review`, and `Done` lists. Team names, leaders, prefixes, labels, members, lists, and cards always come from bootstrap; the project label catalog, permission-aware Quick Action catalog, autocomplete references, and Comments are fetched separately.

## Security

GitLab OAuth uses Authorization Code with PKCE, `api` scope, and single-use encrypted state. Access and rotating refresh tokens are encrypted at rest so durable mutations preserve the real GitLab actor. Browser sessions are random opaque tokens in HttpOnly cookies; PostgreSQL stores keyed digests. Every valid use renews expiry to 14 days from that use. Authenticated mutations require both the session-bound CSRF token and an allowed Origin.
