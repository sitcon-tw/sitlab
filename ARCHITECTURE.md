# SITCON Board Architecture

## Product Boundary

SITCON Board is a focused GitLab-backed workflow for the fixed `sitcon-tw/2027` project. The primary path is GitLab OAuth, primary-team confirmation, quick card creation, movement, assignment, due-date adjustment, and closing. There are no workspace, generic task, password-registration, or arbitrary-project concepts.

## Data Flow

```text
GitLab signed project/group webhooks -> durable webhook inbox
                                             |
Bundled board-directory.yml + GitLab API -> PostgreSQL snapshots + revision
                                             |
                              injected bootstrap JSON + REST + SSE
                                             |
                                         React Board
```

Production traffic is ready only after directory, member, and board snapshots exist. The server injects the complete authenticated bootstrap payload into `index.html`; React renders from that payload before starting background refresh. The development API fallback is `GET /api/v1/bootstrap`.

Project Issue and group Member webhooks are authenticated with GitLab HMAC signing tokens and committed to a durable inbox before acknowledgement. Workers fetch canonical GitLab state instead of trusting webhook payloads. Every visible content or sync-state change advances a PostgreSQL bootstrap revision; unchanged recovery polls only refresh snapshot health. `LISTEN/NOTIFY` fans revisions out across instances and a continuously connected authenticated SSE stream tells browsers to refetch. Three Board reads back the hooks up. An incremental read asks GitLab only for what changed since the last successful one, walking updated_at ascending so a row edited mid-pagination cannot be skipped. A presence sweep enumerates which issues still exist, which is the only way to notice a deletion. A slower full re-read catches drift that changes nothing observable. The cursor is a read position, not a description of content, so a row the merge skipped never holds it back.

## Backend Boundaries

Dependencies point inward: HTTP transport calls application use cases, application packages own narrow ports, infrastructure implements those ports, and domain packages own board, directory, identity, and sync models. The file adapter supplies the repository-owned directory bundled into the image; the GitLab adapter supplies members and issues. PostgreSQL adapters do not import application or transport packages. The composition root is the only package that constructs concrete adapters.

Card mutations write the optimistic card cache and a durable operation in one transaction. A worker resolves the encrypted GitLab OAuth credential for the operation's actor, sends only that operation's stored fields through the GitLab Work Item GraphQL API as that user, then merges the returned canonical Work Item through the same reconciliation rules as webhooks. Field-scoped writes are required for native Quick Actions in descriptions: an unrelated assignee or date operation must never resend and re-execute description commands. The intent can include title, Markdown description, Start/Due dates, labels, GitLab-native multiple assignees, and native lifecycle status. Tag edits accept existing project labels, require exactly one active Team label, and never change lifecycle status; moves and the explicit status control own status changes. PostgreSQL owns manual card positions: only manual sorting sends and changes a browser drop position, while status-only moves omit it and preserve the card's existing manual position. Active Due, Start, and Updated views retain their selected presentation sort. GitLab refreshes preserve same-list manual order, while newly observed cards and external status moves enter at the top of their list. Snapshot merges reject GitLab data older than a completed local mutation, and write a card only when GitLab reports something different, so a re-read of unchanged data neither rewrites rows nor wakes browsers. Pruning compares when a GitLab read last confirmed a card against the instant the read began, both on PostgreSQL's clock, so a card reconciled by a webhook mid-read is kept; a read that reports nothing at all is never treated as an emptied board. The fixed list keys map by name to `Waiting`, `Inbox`, `To do`, `Doing`, `Review`, and `Done`. A GitLab lifecycle missing any of those statuses is a configuration error and fails the read outright, but a single issue set to some other status is quarantined rather than allowed to abort the refresh: the card stays as last known and the board keeps syncing until someone moves the issue on. Legacy workflow labels are filtered from mutations and the label catalog. New cards use a temporary negative IID and position zero; PostgreSQL updates the IID to GitLab's positive value with deferred cascading foreign keys. Failed operations retain the optimistic UI state and can be retried. Background sync stays quiet, but a field the user just edited shows an in-place saving indicator that resolves to a brief saved marker; only offline or failed states surface technical status.

Project labels are read from GitLab with the project token and do not enter bootstrap. Creating, renaming, and deleting a project label runs as the real actor through the GitLab REST label API, so GitLab's own project role decides who may change a project-wide resource; GraphQL is not used because it has no label update or delete mutation. Team-prefixed and legacy workflow names are reserved and rejected before any GitLab call, and a reserved label cannot be renamed even to a legal new name. A card mutation whose labels no longer all exist drops the vanished ones rather than failing permanently, except for a missing Team label, which the board needs to place the card. Card comments and system notes are fetched on demand with the requesting user's OAuth token, and new comments are written synchronously as that user. Comments are not cached in PostgreSQL and are not added to the durable operation queue; a failed submission leaves the browser draft available for an explicit retry.

Child items and linked items follow the same on-demand boundary as comments. Opening a card reads GitLab Work Item hierarchy and link widgets with the requesting user's OAuth token; creating or attaching a Task child, detaching its parent, and adding or removing same-project Issue/Task links are synchronous GraphQL mutations attributed to that user. A linked-item request accepts up to 20 unique targets and the GitLab adapter sends them in one native mutation. Relations do not enter `BoardCard`, bootstrap, PostgreSQL snapshots, or the durable operation queue. Board cards remain GitLab Issues, while children created by the Board are native Tasks and never become lane cards automatically. Attaching a Task that already has a parent is rejected rather than reparented, and detaching removes only the parent relation. Blocking links are exposed when the GitLab tier supports them and otherwise return a stable inline feature-unavailable error.

## Identity And Security

GitLab OAuth uses Authorization Code with PKCE, `api` scope, and a single-use server-side state record. Login is restricted to active members of `sitcon-tw/2027`. Access and rotating refresh tokens are encrypted at rest and resolved only by application use cases that execute durable card mutations or on-demand comment reads and writes as the real actor. Browser authentication uses a random opaque token in an HttpOnly cookie; PostgreSQL stores only a keyed digest. Sessions use a 14-day rolling expiry: every valid request renews both the database expiry and browser cookie. Authenticated mutations require an allowed Origin and a stable, purpose-separated HMAC CSRF token bound to the session ID; bootstrap refreshes never rotate or invalidate it.

## Frontend Ownership

`web/src/features/board` owns Board state, the navigable right-side detail drawer, Tag selection, on-demand Child/Linked Work Item queries and dialogs, Comment queries and drafts, the reusable GitLab-aware Markdown autocomplete, leader bulk-create, multiple-assignee selection, and optimistic reconciliation. Quick Action execution remains native to GitLab: descriptions travel through the actor-scoped Work Item mutation and Comments through the actor-scoped Notes API. The backend exposes GitLab's permission-aware command catalog and normalizes its separate reference searches into an extensible suggestion contract. Linked-item candidate selection is multi-value and submits one batch. Relation removal first updates the TanStack Query cache, performs the actor-scoped API request in the background, and rolls the item back on failure. `web/src/features/onboarding` owns primary-team confirmation. TanStack Query owns server snapshots plus per-card Comment and relationship state, feature state owns unsaved interaction, and bootstrap initialization pre-fills the first render. Team names, leader IDs, title prefixes, member lists, the six ordered board lists, and cards come from the backend.

## Contract Flow

TypeSpec under `api/` is the HTTP source of truth. Generation emits byte-identical OpenAPI for docs and the embedded backend document, plus TypeScript declarations for the web client. Generated artifacts are never edited manually.
